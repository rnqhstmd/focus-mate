## PRD: Phase 2 카드·여행 준비·승차 인식 — 잠정 검토안

> 상태: **잠정안 / 미승인**
> 전제: 사용자의 “다시 진행”이 Phase 2 계속을 뜻하는지는 아직 확인되지 않았다. 이 문서는 개발 착수 승인이 아니며, 구현·브랜치·병합·파일 변경을 수행하지 않았다.
> 전달 상태: Phase 1은 PR2까지 완료됐고 PR2는 OPEN/MERGEABLE이라고 전달받았다. 이번 읽기 전용 검토에서는 원격 상태를 재확인하지 않았다.

### 배경

- 현재 iOS 제품은 저장된 상태에 따라 카드 진입, 최초 정류장 진입, 현재 정류장 메인을 구분한다. 메인에서는 여행 준비·기록·설정·마이페이지의 기본 화면만 열 수 있다. 실제 카드 발급이나 여행 준비는 아직 수행할 수 없다. (AppSnapshot, AppModel, RootView에서 확인)
- 현재 저장값은 카드 발급 여부, 최초 정류장, 현재 정류장뿐이다. 발급 카드 ID, 준비 초안, 승차 인식 상태, 진행 여정은 없다. (AppSnapshot에서 확인)
- 손상되었거나 지원하지 않는 저장 데이터는 초기 상태로 덮어쓰지 않고 이용을 중단한다. 저장 실패 시 기존 상태를 유지하고 성공으로 안내하지 않는다. (LocalSnapshotStore, RootView에서 확인)
- 승인 웹 흐름은 1회 카드 발급, 최초 정류장 설정, 15~360분 여행 선택, 태그·할 일·소리 준비, 승차권 확인, 카드 접촉 인식 순서다. 실제 교통카드 인증이나 실제 버스 운행 정보가 아니다. (FLOWS, MVP, animation-preview에서 확인)
- Phase 2는 승차 접촉 성공까지를 다룬다. 지도에서의 여행 진행, 실제 선택 시간 타이머, 일시정지·재개, 하차, 완료 기록은 후속 단계다. (DEVELOPMENT-PHASES에서 확인)

### 목표

- 최초 사용자가 카드 발급과 첫 출발 정류장 설정을 한 번만 완료하고, 이후에는 저장된 현재 정류장에서 여행을 준비할 수 있게 한다.
- 사용자가 유효한 시간·버스·도착지와 태그·할 일·소리를 확정한 뒤 승차 접촉까지 완료할 수 있게 한다.
- 승차 접촉 성공 순간에 다음 단계로 넘길 정보를 한 번만 보존하여, 화면 전환이나 앱 재실행으로 준비 내용이 소실되지 않게 한다.
- Phase 2가 실제 여행 진행이나 완료 기록을 만든 것처럼 보이지 않게 한다.

### 요구사항

#### 기능 요구사항

- [Must] **P2-FR-1: 집중동행카드 1회 발급**
  - 카드가 없는 사용자는 집중동행카드를 한 번 발급받을 수 있어야 한다.
  - 발급 시 `FM-`과 숫자 8자리로 이루어진 카드 ID와 발급 상태를 보존해야 한다.
  - 발급 후에는 동일한 카드 ID를 승차 접촉에서 사용해야 하며 재발급 흐름을 반복 노출하지 않아야 한다.
  - 기존 카드 도메인의 FR-3/AC-4 중 발급·공통 카드·승차 접촉 부분만 연결한다. 사진 입력과 카드 꾸미기는 Phase 5이므로 기존 FR-3 전체를 완료 처리하지 않는다.

- [Must] **P2-FR-2: 최초 정류장 1회 설정**
  - 카드 발급을 마친 사용자는 앱이 제공하는 가상 정류장의 이름과 진행 방면을 선택해야 한다.
  - 선택값은 최초 정류장과 현재 정류장으로 보존해야 한다.
  - 설정 완료 후 현재 정류장은 읽기 전용으로 표시해야 한다.
  - 앱 내부에서 정류장을 다시 검색하거나 변경하거나 초기화하는 기능을 제공하지 않아야 한다.

- [Must] **P2-FR-3: 현재 정류장 중심의 메인과 준비 진입**
  - 재방문 사용자는 저장된 현재 정류장과 진행 방면을 먼저 확인할 수 있어야 한다.
  - 여행 시작 행동은 기록·설정·마이페이지보다 우선적으로 인식되어야 한다.
  - 메인과 여행 선택 진입은 승인된 지도 우선 시각 계층을 따르되, 실제 지도 이동이나 위치 추적을 제공하지 않아야 한다.

- [Must] **P2-FR-4: 시간·버스·도착지 확정**
  - 사용자는 15~360분 범위에서 1분 단위로 시간을 선택해야 한다.
  - 앱은 선택한 시간과 정확히 일치하는 가상 버스·도착지 후보만 보여줘야 한다.
  - 사용자는 후보 중 하나를 명시적으로 선택해야 준비 단계로 이동할 수 있다.
  - 시간을 변경하면 기존 버스·도착지 선택을 해제해야 한다.
  - 후보가 없거나 후보를 선택하지 않은 상태에서는 다음 단계로 이동할 수 없어야 한다.

- [Must] **P2-FR-5: 태그·할 일·소리 준비**
  - 준비는 태그가 선택되지 않은 상태에서 시작해야 한다.
  - 태그 선택 화면에서는 기존 태그 선택 또는 새 태그 추가만 허용해야 한다.
  - 태그 편집, 최근 할 일 예시, 기본 여행 시간 정보는 태그 선택 화면에 제공하지 않아야 한다.
  - 기존 태그를 선택하거나 새 태그를 저장하면 바로 이번 여행의 할 일 입력으로 이어져야 한다.
  - 할 일은 공백만으로 확정할 수 없으며 최대 80자까지 허용해야 한다.
  - 새 태그 이름은 공백일 수 없고 최대 20자이며, 대소문자·문자 표현 차이를 정규화했을 때 같은 이름은 추가할 수 없어야 한다.
  - 새 태그에서는 승인된 아이콘과 색을 고를 수 있어야 한다.
  - 사용자는 핑크 노이즈, 빗소리, 숲 소리, 버스 주행, 소리 없음 중 하나를 선택하고 미리 들을 수 있어야 한다.
  - 소리 선택은 선택 사항이며 초기값은 `소리 없음`이어야 한다.
  - 준비 화면과 하위 선택 화면을 오가는 동안 시간·버스·도착지·태그·할 일·소리 초안을 유지해야 한다.

- [Must] **P2-FR-6: 간결한 승차권**
  - 모든 필수 준비가 끝난 경우에만 승차권으로 이동할 수 있어야 한다.
  - 잠정 범위에서는 버스 번호, 출발 정류장, 도착 정류장, 여행 시간, 정류장 수, 이동 거리만 표시한다.
  - 태그·할 일·선택 소리는 준비 단계의 확정값으로 유지하되 승차권의 주요 정보로 반복 표시하지 않는다.
  - 이 구성은 현재 프로토타입 및 FLOWS 문서와 충돌하므로 승인 전 확인이 필요하다.

- [Must] **P2-FR-7: 승차 접촉 인식**
  - 사용자는 카드를 단말기 접촉 영역으로 옮기거나 카드 자체를 눌러 승차 인식을 시작할 수 있어야 한다.
  - 접근 가능한 입력에서도 동일한 승차 인식 결과를 얻을 수 있어야 한다.
  - 잘못된 위치에 놓거나, 접촉 전에 화면을 벗어나거나, 앱이 숨겨지면 승차 성공으로 처리하지 않아야 한다.
  - 접촉 성공 후에는 동일 입력의 중복 처리를 막아야 한다.

- [Must] **P2-FR-8: 승차 접촉 체크포인트와 1회 인계**
  - 승차 접촉 성공 순간에 카드 ID, 출발 정류장과 방면, 시간, 버스, 도착지, 태그, 할 일, 소리, 승차 인식 완료 상태를 하나의 재개 가능한 정보로 보존해야 한다.
  - 보존은 승차 연출의 마지막 화면 전환까지 미루지 않아야 한다.
  - 앱이 접촉 성공 후 종료되어도 다음 실행에서 동일한 준비값과 승차 인식 상태를 확인할 수 있어야 한다.
  - 동일 승차 접촉은 한 번만 인계되어야 한다.
  - 이 체크포인트는 Phase 3 여행 시작을 위한 인계이며, 실제 타이머 진도·이동 위치·일시정지 상태를 뜻하지 않는다.
  - Phase 2에서는 접촉 성공 후 실제 여행이 진행되거나 완료된 것처럼 표시하지 않아야 한다.

- [Must] **P2-FR-9: 기존 저장 사용자 보존**
  - Phase 1에서 카드 발급 상태와 최초·현재 정류장을 저장한 사용자는 Phase 2 적용 후에도 같은 정류장과 방면을 유지해야 한다.
  - 새 필드가 없다는 이유로 기존 사용자를 최초 상태로 돌리거나 정류장 선택을 다시 요구하지 않아야 한다.
  - 카드 ID만 없는 기존 발급 상태는 정류장·방면을 유지하며 ID를 한 번 보완하고, 이후 재실행에서는 같은 ID를 유지하는 것으로 제안한다. 재발급·첫 정류장 재설정은 요구하지 않는다.

#### 비즈니스 규칙

- [Must] **P2-BR-1:** 카드 발급은 사용자당 한 번이며 발급된 ID는 이후 승차 접촉에서도 동일해야 한다.
- [Must] **P2-BR-2:** 최초 정류장 검색은 한 번만 허용한다. 현재 정류장의 변경·워프·초기화는 Phase 2에 포함하지 않는다.
- [Must] **P2-BR-3:** 시간, 유효한 버스·도착지, 태그, 공백이 아닌 할 일이 모두 확정되어야 승차권에 진입할 수 있다.
- [Must] **P2-BR-4:** 승차권 확인만으로 진행 여정이나 완료 기록을 만들지 않는다.
- [Must] **P2-BR-5:** 진행 가능한 체크포인트는 승차 접촉이 성공한 순간에만 한 번 생성한다.
- [Must] **P2-BR-6:** 접촉 전 취소·이탈·숨김은 체크포인트를 만들지 않는다.
- [Must] **P2-BR-7:** 손상·미지원 저장 데이터는 명시적 복구 기능 없이 덮어쓰거나 재발급 상태로 바꾸지 않는다. Phase 1의 보호 동작을 유지한다.
- [Must] **P2-BR-8:** 저장 실패는 성공으로 안내하지 않으며, 기존에 보존된 사용자 상태를 유지한다.
- [Must] **P2-BR-9:** 실제 GPS, 실제 교통카드 인증, 실시간 운행·도착 정보를 제공하는 것처럼 표현하지 않는다.

#### 디자인 명세

다음은 승인된 경험을 재현하기 위한 디자인 명세다. 연출 수치 자체를 제품 완료 판정으로 사용하지 않는다.

- 승차 단말기 상단에는 `Focus Mate`와 사용자의 실제 로컬 `HH:mm`을 표시하며 버스 번호는 표시하지 않는다.
- 승차 대기 문구는 `작은 시작이 오늘을 바꿔요.`를 사용한다.
- 인식 후에는 현재 카드 이름과 카드 ID를 표시한다.
- 일반 동작은 접촉 이동 300ms, 인식 유지 1400ms, 페이드 450ms다.
- 동작 줄이기에서는 접촉 이동·페이드·햅틱을 생략하고 인식 유지와 상태 안내를 남긴다.
- 메인은 지도 영역과 현재 정류장, 여행 시작을 중심으로 구성한다. 실제 MapKit 지도와 이동 상호작용은 Phase 3 범위다.

### 사용자 시나리오

#### 정상 흐름: 신규 사용자

1. 카드가 없는 사용자가 앱을 연다.
2. 집중동행카드를 발급받고 카드 ID를 확인한다.
3. 최초 출발 정류장의 이름과 방면을 한 번 선택한다.
4. 현재 정류장 중심 화면에서 여행 준비를 시작한다.
5. 15~360분 중 시간을 선택하고 정확히 일치하는 버스·도착지를 선택한다.
6. 기존 태그를 고르거나 새 태그를 추가한 뒤 할 일을 입력한다.
7. 소리를 선택하거나 `소리 없음`을 유지한다.
8. 간결한 승차권을 확인한다.
9. 카드를 단말기에 접촉한다.
10. 승차 인식 성공과 함께 준비값이 보존되고 Phase 3용 인계 상태에 도달한다.

#### 정상 흐름: 재방문 사용자

1. 저장된 현재 정류장과 방면이 읽기 전용으로 표시된다.
2. 카드 발급이나 최초 정류장 선택을 반복하지 않고 여행 준비로 진입한다.
3. 승차 접촉 전까지 기존 현재 정류장은 바뀌지 않는다.

#### 예외 흐름

- 해당 시간의 후보가 없으면 다른 시간을 선택하도록 안내하고 준비 진행을 차단한다.
- 시간을 바꾸면 이전 버스·도착지 선택은 해제된다.
- 태그가 없거나 할 일이 공백이면 승차권 진입을 차단한다.
- 새 태그 이름이 공백·20자 초과·중복이면 저장하지 않고 이유를 안내한다.
- 소리 미리듣기에 실패해도 준비값은 유지하며 다른 소리 또는 `소리 없음`을 선택할 수 있다.
- 접촉 영역 밖에 카드를 놓거나 접촉 도중 화면을 벗어나면 인식 성공으로 처리하지 않는다.
- 접촉 성공 뒤 화면 전환 전에 앱이 종료되어도 인계 상태는 남는다.
- 손상되거나 지원하지 않는 기존 데이터가 있으면 카드 재발급이나 신규 상태 저장으로 원본을 덮어쓰지 않는다.

### 영향 범위

- Phase 1의 카드 진입 화면은 실제 1회 발급 경험으로 확장된다.
- Phase 1의 최초 정류장 진입 화면은 실제 가상 정류장·방면 선택으로 확장된다.
- 현재 정류장 메인은 읽기 전용 정류장 정책을 유지하면서 실제 여행 준비 진입점을 제공한다.
- Phase 1 저장 사용자는 최초·현재 정류장과 방면을 그대로 유지해야 한다.
- 카드 ID와 준비·승차 인계 정보가 새롭게 보존 대상이 되지만, 손상·미지원 데이터 보호 규칙은 약화하지 않는다.
- 기존 카드 도메인 FR-3/AC-4는 부분 반영만 가능하다. 카드 사진 입력이 빠지므로 해당 기존 요구사항 전체는 완료가 아니다.
- journey 도메인의 실제 분 타이머·MapKit·생명주기 진도 처리는 여전히 미반영 상태다.

  **Then:** `FM-`과 숫자 8자리인 카드 ID가 생성·보존되고 최초 정류장 선택으로 이어진다.

- 하차 접촉, 도착 요약, 선택 메모
- 완료 기록, 잔디, 기간·태그 분석
- 카드 사진·색·배치 편집과 카드 사진 입력
- 설정·마이페이지의 기능 완성

- 여행 완료를 흉내 내는 압축 진행이나 가짜 완료 기록

### 확인된 문서·제품 충돌

1. **승차권 정보 구성**
   - 현재 프로토타입과 FLOWS는 승차권에서 할 일 확인을 포함한다.
   - 기존 승인 선호와 이번 요청은 버스 번호·출발/도착·시간·정류장 수·거리만 남기는 간결한 승차권을 요구한다.
   - 기존 사용자 지시(승차권에서 태그·할 일 제거)를 우선해 간결한 구성을 적용한다. 같은 선택을 다시 확인하지 않는다.

2. **최초 정류장 선택 후 이동 위치**
   - 현재 프로토타입은 최초 정류장 확정 후 곧바로 시간 선택으로 이동한다.
   - MVP 문서는 첫 이용을 카드 발급·첫 정류장 설정까지로 구분하고, 이후 현재 정류장 메인에서 여행을 시작하는 흐름으로 읽힌다.
   - 현재 승인 프로토타입과 FLOWS의 명시적 성공 경로를 따라 최초 설정 직후에는 시간 선택으로 이어지고, 이후 재실행은 저장된 현재 정류장 메인에서 시작하는 것으로 제안한다.

3. **손상 카드 데이터 처리**
   - 웹 프로토타입에는 저장된 카드를 읽지 못했을 때 다시 발급하는 표현이 남아 있다.
   - 현재 iOS 기반은 손상·미지원 데이터를 보존하고 쓰기를 차단한다.
   - 이번 요청에 따라 Phase 2는 현재 iOS 보호 규칙을 유지하며 웹의 즉시 재발급 동작은 가져오지 않는다.

4. **도메인 상태 문서의 시점 차이**
   - card/journey context 문서는 네이티브 iOS가 미착수이거나 Swift 소스가 없다고 기록한다.
   - 현재 Phase 1 문서와 iOS 제품은 앱 기반·진입 분기·저장 보호가 이미 존재함을 보여준다.
   - 본 잠정안은 현재 iOS 제품과 Phase 1 문서를 현재 상태의 근거로 사용했다.

## 확인이 필요한 사항

1. “다시 진행”은 어떤 작업을 의미하나요?
   - 맥락: Phase 1은 PR2까지 완료됐다고 전달됐고, 다음 제품 단계는 Phase 2입니다. 이 선택 전에는 본 PRD를 승인하거나 개발을 시작할 수 없습니다.
   - 유형: 선택
   - 선택지:
     - (a) Phase 2 계속 (권장) — 이 잠정안을 확정하는 Q&A를 이어갑니다
     - (b) Phase 1 재검증 — Phase 2 범위를 확정하지 않고 기존 결과를 다시 확인합니다
     - (c) Simulator 실행 — 제품 동작을 직접 확인하는 별도 작업으로 진행합니다
     - (d) 직접 입력 — 위 선택지 외 다른 방식을 직접 입력합니다


그 밖의 흐름은 기존 사용자 지시와 승인 프로토타입을 우선해 제안에 반영했다. Phase 2로 진행한다는 답변 전에는 새 구현을 시작하지 않는다. 이후 실제 파이프라인의 PRD 확인은 이 전체 범위를 검토 가능한 형태로 정리한 뒤 수행한다.

후속 실행이 승인되는 경우 기존 `gx-tdd ALL / standard` 선호를 유지한다. 별도 개발 계획이나 일정은 만들지 않는다.

## 오케스트레이터 보완

원본 PO 초안이 다시 물었던 승차권 정보 구성은 이전 사용자 지시로 이미 결정돼 있어 추가 질문에서 제거했다. 최초 설정 뒤 시간 선택은 현 프로토타입/FLOWS에 맞췄다. 기존 발급 사용자의 카드 ID 보완은 설정 보존·재발급 방지 목적의 제안이며 실제 구현과 저장 스키마는 아직 정하지 않았다.
