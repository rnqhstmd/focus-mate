## 색상·서체·컴포넌트

- HTML 공통 패널 (`:2`)은 #0A0A0A, radius24, 약한 흰 테두리, padding22, 좌우12/하단25이며 주 CTA는 흰 배경/검정 글자다. 기본 `.bordered`/`.borderedProminent`를 사용하는 메인·시간·요약은 이 규칙과 다르다. 버튼 모양만 바꾸면 화면 골격 차이는 해결되지 않는다.
- `PreparationView.swift:123`의 #0.035/radius24 패널과 전용 타이포·태그 칩은 이미 맞춤 구현이다. 모든 화면이 기본 UI라는 결론은 틀리며, 공통 셸 적용 시 이 화면을 퇴행시키지 않는다.
- `ArrivalBriefingView.swift:38`, `JourneyView.swift:162`에는 이미 상단 회색→검정 LinearGradient가 있다. “앱에 그라데이션이 없다”가 아니라 **장면별 종류/위치/높이/불투명도가 다르다**가 정확하다.
- HTML 단말기 초기 CSS (`:254`)의 녹색 그라데이션은 `:292`의 `.phone .fare-reader { background:#1b1d1e }`에서 덮인다. 최신 검정 단말기를 녹색 구형으로 되돌리면 안 된다.
- `JourneyMapView.swift:42`는 파란 원형 방향 표시를 사용한다. Pen의 일러스트와 동일 기호인지 별도 대조 필요. 지도 이동/방향 기능을 없애고 장식 버스로 교체하는 것은 이번 범위가 아니다.
- HTML/문서의 안내 서체는 서울알림체다. 현재 화면에는 `.largeTitle/.title/.headline`과 별도 PreparationTypography가 혼재한다. 파일 전체에 일괄 font를 덮기보다 안내/수치/본문/버튼별 대응표로 정리해야 한다.

HTML 진동은 브라우저 `navigator.vibrate`의 의도 표현이다. iPhone에서 동일하게 재생됐다는 증거는 아니다. CoreHaptics의 파형·강도는 숫자만 복사해서 동등해지지 않으므로 실제 기기에서 짧은 펄스/쉼/끝 탭의 체감을 확인해야 한다. 이번 감사에는 물리 기기 확인이 없다. 시간 눈금자 등 추가 진동은 양쪽에 명시 근거가 확인되지 않아 새 요구로 만들지 않는다.

## 동기화 작업 경계와 검증 기준

1. 메인→시간 선택→집중/일시정지→요약의 화면 골격을 우선 맞춘다. 카드/준비/기록·프로필은 기존 맞춤 구현을 살려 후속 정렬한다.
2. 공유할 대상은 화면 셸, 패널/CTA/텍스트/그라데이션 토큰이다. AppModel, 저장, 시간 계산, 후보 계산, 승하차 인식, 위젯 게시 계약은 변경 대상이 아니다.
3. 승인 화면별 같은 viewport/상태/데이터의 Pen 또는 최신 HTML 참조와 네이티브 캡처를 나란히 비교한다. 정적 비교는 계층·여백·색·그라데이션, 영상은 전환·카드 이동, 기기는 햅틱을 담당한다.
4. 큰 글자/Reduce Motion/저장 실패/진행 여정 확인 상태를 유지한다. 시안을 맞추려고 텍스트를 고정 높이로 잘라내거나 시스템 접근성을 없애지 않는다.
5. DEBUG 실패 주입 버튼의 검은 사각형이 캡처에 노출된 경우 이를 시안 차이로 오인하지 않는다. 대표 화면 캡처는 진단 overlay 표시 여부를 명시해야 한다.

추가 기준 파일 질문은 없다. 사용자가 Pen+HTML을 지정했다. 다만 기존 문서와 HTML의 Reduce Motion 햅틱 규칙 충돌은 구현 전 계약에 기록하고, 표현 변경이 기능 정책 변경으로 번지지 않도록 분리해야 한다.

결론: 이 보고서의 최초 상세 Pen 대조는 **작업트리 Pen**을 대상으로 했다. 사용자가 말한 “기존 Pen”을 원본 체크아웃 파일과 완전히 같은 것으로 간주해서는 안 된다. 구현 기준표에는 프레임 ID와 어느 파일을 사용했는지 함께 고정해야 한다. 최신 HTML의 명시적 후속 결정과 일치하는 작업트리 변경을 유지하고, 원본 전용 최종 아이콘은 별도 승인 자산으로 보존하는 것이 안전하다. 두 파일을 통째로 상호 복사하지 않는다.
