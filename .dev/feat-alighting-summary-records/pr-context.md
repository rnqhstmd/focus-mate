## 배경
- 타이머가 0이 되면 나가는 길이 없는 임시 도착 화면("도착했어요")만 떠서 앱을 다시 켜야 메인으로 갔다. 이 때문에 W09 전에는 TestFlight 포함 외부 배포가 금지돼 있었다(W07 출시 게이트).
- 메인의 "도착한 여정이 있어요" 카드는 '새 여정 시작'만 있어 완료한 여행이 기록 없이 사라졌다.
- 완료 기록·메모 저장 규칙(W08)은 있었지만 어떤 화면도 호출하지 않았고, 기록 화면은 빈 화면이었다.
- 마이페이지 최대 글자 크기 UI 테스트 2건이 main에서도 실패하고 있었다.
- 범위는 W09a(하차·요약·기록·메모)이며 분석 화면은 W09b로 분리했다(2026-10-15 사용자 결정). 하차를 미루고 새 여정을 시작하는 경로는 두지 않고, 예시 기록은 앱에 노출하지 않는다(사용자 결정).

## 요구사항
- journey FR-12(AC-14): 도착 안내 → 확인 → 하차 태그. 하차 접촉 성공 1회에만 완료 기록·도착 정류장·재개 정보 제거를 한 번에 저장, 중복 무시, 실패 시 상태 불변.
- records FR-6(AC-7 중 요약·기록·메모): 하차 후 요약에서 200자 선택 메모, 기록 화면의 연간 일합계 5단계 잔디·날짜별 최신순 10개·연도 탐색·메모 수정, 예시와 실제 분리.
- card FR-5 회귀: 최대 글자 크기에서 마이페이지 주요 항목 도달·설정 왕복.
- 수용 기준 34건(G-W-T): .dev/feat-alighting-summary-records/prd.md

## 설계 요점
- 하차 저장은 순수 함수 하나(AppSnapshot.alightingActiveJourney)로 기록 생성·도착지 반영·여정 제거를 한 후보로 만들고 1회 저장한다(BR-3). 저장 형식 v4 변경 없음.
- 도착 저장의 주인은 타이머 하나다. 확인을 누르면 타이머가 재시도하고, 모델은 저장본이 도착 상태일 때만 하차 태그로 보낸다(재실행 시 도착 카드 보장).
- 하차 태그는 승차 태그 컨트롤러를 클로저로 일반화하고 화면을 CardTagScreen(CardTagKind)으로 추출해 재사용한다. 하차 저장 뒤 어떤 중단 경로에서도 모델 상태(alightingSummary)로 판단해 요약으로 보낸다(설계 비판 MUST).
- 요약은 메모리 전용이라 재실행하면 요약 없이 메인이다.
- 기록 화면 계산(RecordsCalendar·RecordsBrowser)과 메모 제한(RecordMemoDraft)은 순수 타입으로 분리해 날짜 경계를 단위 테스트로 고정했다. 잔디는 VoiceOver 조정 요소 1개다.
- Live Activity(W15)는 도착 시 기존 종료 경로를 확인만 했다(코드 변경 없음).
