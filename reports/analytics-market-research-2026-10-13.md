# 집중 앱 통계 화면 시장 조사와 분석 화면 권장안

조사 기준일: 2026-10-13. 대상 제품: Focus Mate (iOS, 가상 버스 집중 타이머).
근거 등급: **[확인]** 공식 스토어 설명·공식 도움말·직접 발췌 확인 / **[스니펫]** 검색 결과 요약만 확인 / **[미확인]** 해당 항목을 확인하지 못함.

## 0. 리서치 목적과 범위

- 목적: 현재 기록 화면(연간 잔디, 날짜별 목록)과 분석 화면(주간·월간 합계, 횟수, 태그 필터, 도넛)에 추가할 항목을 정한다.
- 제약: 이미 저장하는 완료 기록 필드만 사용한다. 위치·앱 사용량은 쓰지 않는다. 포기한 여행은 기록하지 않으므로 제외한다. 예시 데이터는 실제 데이터와 분리한다. 동작 줄이기와 다크 UI를 지킨다.
- 기존 기능 확인: 분석에는 주간·월간 합계, 횟수, 여행한 날 수, 평균, 태그 도넛, 같은 경과 기간 비교가 이미 있다. 아래 권장안은 이 항목과 겹치지 않도록 정했다.

### 공통 패턴 (조사 범위 안에서의 관찰)

- 기간 전환(일·주·월·년)은 거의 모든 앱이 제공한다. 우리 앱도 주·월을 제공하므로 **연간 요약**과 **기간 간 비교 방식**이 차이 포인트다.
- 태그별 시간 비중은 여러 앱이 제공하지만, **시간 흐름에 따른 태그 추이**는 Focus To-Do의 추이 차트 정도만 확인했다.
- 스트릭은 Tomodoro·Foku·FocusLab 등에서 흔하다. 다만 Opal은 스트릭 상실 조건을 경고하고 있어 손실 불안과 연결된다.
- 시간대 분석은 Immerse(최적 작업 시간대 패턴), Forest 리뷰("what days and what times")에서 확인된다. 우리 앱은 완료 시각을 저장하므로 실현 가능성이 높다.
- 완료율·집중 점수·앱 사용 기반 지표는 Opal, Rize, FocusLab, Immerse에 있다. 우리 앱은 포기 기록을 저장하지 않고 방해 데이터도 없으므로 그대로 따라갈 수 없다.

### 2-2. 니즈 정리

1. **언제 집중하는지 알고 싶다.** 요일과 시간대 분석은 칭찬받는 기능이고 요청도 많다. 우리 앱 기준으로는 시간대 분석이 가장 직접적인 요구다.
2. **기간을 자유롭게 넘나들며 보고 싶다.** 일·주·월·년 전환과 연간 요약이 기대치다.
3. **태그가 시간에 따라 어떻게 바뀌는지 보고 싶다.** 현재 도넛은 한 기간의 비중만 보여준다. 추이는 아직 빈칸이다.
4. **이전 기준과 비교하고 싶다.** 사용자는 설정값이 아니라 지난 기간 평균이나 장기 평균과 비교하길 원한다.
5. **스트릭은 동기를 주지만 끊김은 불안을 만든다.** Opal 도움말은 스트릭을 잃는 조건을 경고한다. 블로그 글은 끊김이 포기로 이어진다고 주장하지만 근거는 약하다 [스니펫].
6. **기록은 안전해야 하고 나중에 꺼낼 수 있어야 한다.** Be Focused 리뷰에서 기록 소실과 내보내기 요구가 확인된다.
7. **쌓인 기록이 많아져도 화면이 빨라야 한다.** Forest 리뷰에서 데이터 누적 후 느려짐이 언급된다. 우리 기록 화면도 날짜별 10개씩 펼치는 구조를 유지해야 한다.

### 3-2. 항목별 정의

공통 규칙: 모든 지표는 **완료 기록만** 쓴다. 포기·진행 중 여행은 제외한다. 예시 기록·예시 메모·예시 분석은 실제 저장 값과 분리해 같은 함수로 계산하되 '예시'로 표시한다. 날짜는 완료 당시 기기 현지 날짜를 쓴다. 차트 애니메이션은 동작 줄이기에서 끈다. 값은 색 외에 숫자와 텍스트로도 제공한다.

**R1. 시간대 분포 (분석, 우선순위 1)**
- 표시: 선택한 주 또는 월 안에서 시간대별 완료 분 합계를 막대 4개로 보여준다. 최다 구간을 한 문장으로 요약한다.
- 구간: 새벽 00:00~05:00, 오전 05:00~12:00, 오후 12:00~18:00, 저녁 18:00~24:00.
- 기준 시각: 현재 문서에서 확인되는 것은 **완료 시각**이다. 시작 시각 필드는 문서에서 확인하지 못했다. 시작 시각을 저장하지 않으면 라벨을 "마친 시간대"로 쓴다. 시작 시각을 추정하려면 완료 시각에서 선택 분을 뺀다. 이 값이 실제 시작과 일치하는지는 확인이 필요하다.
- 값: 구간별 Σ minutes(선택 분 합계). 비중 = 구간 분 ÷ 기간 총 분.
- 최다 구간: 동점이면 가장 최근 완료 기록이 속한 구간을 고른다.
- 표시 조건: 선택 기간의 완료 기록이 3회 미만이면 "기록이 더 쌓이면 보여요"를 표시한다.
- 주의: 30초로 압축한 시연 시간이 아니라 저장된 선택 분을 쓴다. 시간대는 집중 성과가 아니라 "사용 패턴"으로만 해석한다.

**R2. 기간별 태그 추이 (분석, 우선순위 2)**
- 표시: 기존 도넛 아래에 기간 안 버킷별 누적 막대를 둔다. 주간은 월~일 7개 버킷, 월간은 1–7일·8–14일·15–21일·22일~말일의 4~5개 버킷이다.
- 값: 버킷 × 태그별 Σ minutes. 태그 이름과 색은 저장 당시 값을 쓴다(기존 규칙).
- 태그가 5개를 넘으면 상위 4개와 "기타"로 묶는다. 한 태그를 누르면 기존 태그 필터와 같은 방식으로 연동한다.
- 표시 조건: 태그가 1개뿐이면 막대 대신 "태그가 하나라 비교할 항목이 없어요"를 보여준다.

**R3. 활동일과 연속일 (기록, 우선순위 4)**
- 활동일 집합 D = 완료 기록이 1회 이상인 로컬 날짜들.
- 이번 주 활동일 = 이번 주(월~일) 중 D에 속한 날 수. 표시는 "n/7일"이다.
- 현재 연속일: 오늘이 D에 있으면 오늘부터, 없으면 어제부터 거슬러 올라가 끊기지 않은 날 수. 오늘 기록이 아직 없는 상태는 "끊김"이 아니라 "오늘 아직"으로 쓴다.
- 최장 연속일: D를 정렬한 뒤 가장 긴 연속 구간의 길이.
- 배치: 연간 잔디 위 숫자 두 개로 둔다. 잔디가 이미 날짜별 활동을 보여주므로 스트릭은 보조 정보다.
- 금지: "연속이 끊겼어요" 같은 손실 문구. 기본 강조는 '이번 주 활동일'로 두고 연속일은 보조로 둔다.
- 근거: 스트릭은 Tomodoro·Foku·FocusLab 등에서 흔하다 [스니펫]. 손실 불안은 Opal 도움말 경고와 블로그 주장에서 확인되지만 근거는 약하다.

**R4. 자주 가는 노선과 길이 패턴 (분석, 우선순위 3)**
- 노선 키: (버스 번호, 출발 정류장 이름, 도착 정류장 이름). 키별 완료 횟수 상위 3개를 보여준다. 동점이면 가장 최근 완료일이 있는 노선을 앞에 둔다.
- 길이 구간: 15–30분, 31–60분, 61–120분, 121–240분, 241–360분. 구간별 기록 수와 비중을 보여준다.
- 연결: 노선을 누르면 해당 노선의 기록 목록으로 간다. 기존 최근 여행 연결 방식을 재사용한다.
- 주의: 정류장 이름 표기가 다르면 같은 노선이 나뉠 수 있다. 저장 이름 그대로 쓴다고 명시한다.
- 근거: Opal 커뮤니티의 "가장 많이 쓴 항목" 요청 [확인, 요약]. 버스 노선이라는 세계관과 맞는다는 점은 우리 해석이다.

**R5. 기간 요약 카드 (기록·분석, 우선순위 6)**
- 표시: 연도 헤더 아래 또는 분석 상단에 고정 6개 항목을 보여준다.
  1. 총 완료 분 (기간 내 Σ minutes)
  2. 완료 여행 수
  3. 활동일 수 (D 중 기간에 속한 날)
  4. 최장 연속일 (R3, 기간 내로 자름)
  5. 최다 태그 (기간 내 분 합계 1위, 동점이면 최근 사용 태그)
  6. 자주 가는 노선 1개 (R4)
- 최적 시간대(R1)는 기간이 4주 이상일 때만 넣는다.
- 공유 이미지는 만들지 않는다. 후순위로 둔다.

**R6. 직전 기간 평균 대비 (분석, 우선순위 5)**
- 대상: 완료된 주 또는 월. 진행 중인 기간은 기존 "같은 경과 날짜" 비교를 유지한다.
- 기준선: 직전 4개의 같은 길이 기간 총 분의 평균.
- 결정 필요: 기록이 없는 기간을 평균에 0분으로 넣을지, 빼고 계산할지. 제안은 **사용 시작 이전 기간은 제외하고, 사용 시작 이후 기록 없는 기간은 0분으로 포함**이다. 이 규칙은 전략 단계에서 확정한다.
- 표시: "최근 4주 평균보다 +x분 (±y%)". 직전 유효 기간이 2개 미만이면 "비교 불가"를 표시한다.
- 근거: Opal 커뮤니티의 지난 주·장기 평균 비교 요청 [확인, 요약]. 설정값 대신 실제 기록과 비교하는 방식이 기존 "같은 경과 날짜" 비교의 확장이다.

**R7. 메모 회고 (분석, 우선순위 7)**
- 표시: 기간 안에서 메모가 있는 완료 기록 수와 최근 3개. 각 항목은 날짜·태그·메모 첫 줄 일부를 보여준다.
- 연결: 항목을 누르면 기존 기록 화면의 해당 날짜와 메모 편집으로 간다.
- 프라이버시: 메모 목록은 기본 접힘으로 두고 펼칠 때만 보여준다.
- 근거: Forest Timeline의 "Revisit your focus journey" 기능 [확인, 스토어 설명]. 우리는 메모 기능이 이미 있어 추가 데이터가 필요 없다.

## 5. 전략 단계에서 검토할 질문

1. 시간대는 "마친 시간"으로 둘지, 시작 시각을 저장해 "집중 시작 시간"으로 둘지 정해야 한다. 데이터 모델에서 시작 시각 필드 유무를 먼저 확인한다.
2. 연속일을 기본 표시할지, '이번 주 활동일'을 기본으로 둘지 정해야 한다. 잔디와 역할이 겹친다.
3. 직전 기간 평균에서 기록 없는 기간을 0분으로 포함할지 결정해야 한다.
4. 메모 회고에서 메모 발췌를 몇 글자까지 보여줄지, 기본 접힘을 유지할지 결정해야 한다.
5. 기록이 수백 건으로 늘었을 때 집계를 매번 전체 계산할지, 캐시나 요약 저장을 쓸지 정해야 한다. Forest 사용자의 성능 저하 불만을 고려한다.
6. 예시 분석을 같은 계산 함수로 돌릴지, 별도 고정 데이터로 둘지 정해야 한다. 실제 데이터와 분리 원칙을 유지한다.

## 6. 권장 액션

1. R1 시간대 분포를 먼저 설계한다. 시작 시각 필드 유무를 확인하고, 라벨을 "마친 시간대"로 할지 결정한다.
2. R2 태그 추이는 기존 도넛과 같은 집계 함수를 재사용하도록 설계한다.
3. R4와 R3는 낮은 공수로 함께 넣는다. 기록 화면과 분석 화면에 각각 배치한다.
4. R5 요약 카드는 R1·R3·R4 구현 후에 넣는다.
5. R6의 기준선 규칙(빈 기간 처리)을 전략 단계에서 확정한 뒤 구현한다.
6. 후순위 항목 중 CSV 내보내기는 기록 백업 설계와 함께 다시 검토한다.
7. 구현 뒤 기록 수 100건 이상과 빈 기록 상태에서 집계 속도와 표시를 확인한다.
